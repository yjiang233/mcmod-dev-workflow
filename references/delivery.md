# 提交、发布与知识库同步执行细节

本文件是 `SKILL.md` 红线被**用户明确指令解除后**的操作清单，不重复红线本身。执行前逐项核对。文中带「记录时间」的路径、分支与版本都是本机实例，换工程时按 `PORTABILITY.md` 替换或删除。

## 双版本仓库的发布编排

当仓库采用「主线 = 新版本 NeoForge，另一分支 = 旧版本 Forge」的布局时（记录时间 2026-11-12 的实例：`main` = MC 1.21.1 / NeoForge，`1.20.1` 分支 = Forge）：

- 日常开发**只改主线**，移植到旧版本分支由 AI 负责同步，用户不手动改。
- 用户说「提交 / 打包 / 发布」时，两个分支都要同步提交、各打各的 jar、各发一个 Release。
- Release tag 按 MC 版本区分，例如 `v1.0.0-mc1.21.1` 与 `v1.0.0-mc1.20.1`。
- 执行顺序建议：先确认两个分支工作区都干净 → 分别构建通过 → 分别提交 → 打 tag → 发 Release。任何一步失败就停下报告，不要带病继续。

## 旧版本分支移植注意（仅当该分支存在时适用）

- 构建工具链不同（ForgeGradle 6 + Java 17），gradle 命令需带 `GRADLE_USER_HOME` 指向纯 ASCII 路径。
- 第三方 mod jar 多为 SRG 映射，全部走 `fg.deobf(...)`；反混淆后要跑 refmap 修补脚本修 mixin 映射。
- 包名与注册体系需要批量映射（`neoforged.*` → `forge.*`、`BuiltInRegistries` → `ForgeRegistries`、`ResourceLocation` 构造器差异、流体 API 路径差异）。
- 用 `runServer` 验证，不要复用新版本分支的客户端存档目录。
- 移植前用 `javap` 核对关键 API 签名是否跨版本一致，能省掉大量盲改。

## 知识库同步规范

- 库路径**从用户长期记忆或项目约定里读取，不要硬编码**（示例结构：`<知识库根>/项目/<项目名>/`；换机器时按 `PORTABILITY.md` 替换）。
- 每个项目一篇主笔记：`项目/<项目名>/<项目名>.md`，维护功能表、技术栈、踩坑小节。
- 开发日志：同目录 `更新日志.md`，**按日期倒序**在标题下插入新章节，每章写「改动 + 踩坑 + 待办」。
- 踩坑要写清**症状和根因**，不只写「已修复」——下次遇到同样症状才搜得到。
- 常有「只写了工作区 `.workbuddy/memory` 就算完成」的失误，用户对此明确不满；两边都要写，Obsidian 是给人看的，工作区记忆是给 AI 读的。

## 交互与代码约定

- 删除多余标语、说明文字与次要标签；删完界面看不懂，就重新设计布局而不是把字加回来。
- 每次修改同时兼顾**用户体验、开发体验、AI Agent 使用体验**，三者都要提升且不破坏现有功能。
- 代码不写注释。
- 凭据只从本机凭据文件读取，不写进技能、代码、笔记正文或任何会进仓库的文件。
